# Oyi Backend — WhatsApp inbound persistence defect (42P10): root cause

Branch `fix/whatsapp-inbound-persistence-conflict-target` (base: Backend production `main` @ `44afac3182a709de63642359a783709ae6a0f435`). Not merged, not deployed, nothing replayed.

## Symptom
Office stored 56+ inbound WhatsApp messages since 2026-08-22 (47 distinct provider ids); Oyi Backend's `oyi_communications` holds only 7 inbound WhatsApp rows (all 2026-08-22) and none after 2026-08-26. Status callbacks do persist (`oyi_communication_events`: sent 47 / delivered 56 / read 54). Office logs `whatsapp_webhook.backend_forward_failed` (8 s timeout) intermittently — a different, intermittent symptom (see "Not changed").

## Root cause (reproduced)
`src/services/communicationRuntime/inboundEventPipeline.ts` persisted the inbound message with
`supabaseAdmin.from("oyi_communications").upsert(row, { onConflict: "provider,provider_message_id,direction", ignoreDuplicates: true })`.
PostgREST translates that to `INSERT … ON CONFLICT (provider, provider_message_id, direction) DO NOTHING`. The only unique index on those columns, `uq_oyi_communications_inbound_provider_message` (migration `20260823100000_oyi_inbound_reply_loop.sql`), is a **partial** index (`WHERE provider_message_id IS NOT NULL AND direction = 'inbound'`). PostgreSQL cannot infer a partial index from a bare column list (the statement would have to repeat the predicate, which PostgREST cannot express), so every execution fails with **`42P10: there is no unique or exclusion constraint matching the ON CONFLICT specification`**. The pipeline returned `ok:false` (`inbound_event_persist_failed`) and the route answered 200 `{ok:false}`: nothing persisted, no classification, no opt-out governance, no goal wake, no thread.
Evidence: (a) planner-only `EXPLAIN` of the same statement against the production Backend database returns 42P10 (nothing executed or written); (b) the committed smoke test reproduces the exact legacy statement against a disposable Postgres loaded with the Backend's own migrations and gets 42P10 with zero rows; (c) the same test run against the unmodified production build fails at the first inbound message with that error (negative control).

## Secondary defect found while fixing (same file)
Every decision event of one inbound message was inserted into `oyi_communication_events` with `provider_event_id = <the message id>`, and that table has `uq_oyi_communication_events_provider (provider, provider_event_id) WHERE provider_event_id IS NOT NULL`. Only the first event per message (`inbound.classified`) could ever be stored; `governance.opt_out_recorded`, `goal.wake_triggered` and the new `inbound.replayed` were silently dropped as "duplicate key". Consequence for governance: the STOP opt-out itself (`oyi_communication_opt_outs`, full unique constraint) was recorded correctly, but its audit event was lost. Fix: the event type is appended to the id (`<message id>:<event type>`), which keeps idempotency per (message, event type). No historical rows are affected (no inbound decision events exist in production).

## The fix (smallest compatible with the existing partial index; no migration)
1. Persist with a plain **INSERT**. The partial unique index remains the arbiter; concurrent/duplicate deliveries yield exactly one row and the loser receives `23505`.
2. `isInboundDuplicateError(error)` treats **only** `23505` on `uq_oyi_communications_inbound_provider_message` as "duplicate" (returns `ok:true, duplicate:true`, no re-processing). Any other error (other unique index, CHECK violation, network) is a real failure reported as `ok:false` — nothing is mistaken for a duplicate.
3. Decision events get type-qualified idempotency ids (secondary defect above).
4. **Replay mode** (for recovering history later, see the release plan): `processInboundEvent(event, { replay: true })` — set on the authenticated Office route only by an explicit boolean `replay:true` — persists with the message's ORIGINAL timestamp, classifies, and still honours a historical STOP, but **never wakes goals** (no goal evaluation, no automated follow-up, no outbound message can result) and records `inbound.replayed` with `goal_wake: skipped_replay`. Idempotent on the provider message id like any live delivery.
No change to the intelligence architecture, classifier, goal runtime, WhatsApp autonomy, Office bridge contract, Meta credentials or CRM.

## Tests (`npm run smoke:whatsapp-inbound-persistence-postgres`; real PostgreSQL 17 + PostgREST, Backend migrations, fixtures only)
0 legacy statement ⇒ 42P10, nothing persisted; A live message persisted (direction/status/outcome, `inbound-<id>` correlation, thread association, `reply_to_message_id` to the latest outbound, classification, decision event); B duplicate delivery ⇒ `duplicate:true`, one row, no second event; C 12 concurrent deliveries ⇒ exactly one winner, 11 duplicates, zero errors; same text with different ids ⇒ two rows; D STOP ⇒ `unsubscribe`, opt-out recorded, **both** decision events stored; E live message wakes the goal watching its thread, while a replay does not (even with a goal waiting), keeps the original timestamp, is idempotent, no-ops when the message already exists, honours a historical STOP, and creates no outbound row; F only the idempotency index means duplicate, a CHECK violation is a reported failure; G route wiring (explicit `replay:true`; conflict target removed). Negative control: the suite fails against `44afac3` with the 42P10 reason.

## Not changed (evidence-based)
* The intermittent 8,000 ms forward timeouts: not caused by this defect (the failing path returned immediately). Probable Backend wake-up/latency; Backend logs/plan are not accessible, so it is unproven. Office already continues CRM intake on a failed forward. A future change (async forward / queue) would be an architecture decision and is not part of this fix.
* The `goal_active`/`matched_outbound` response fields keep their existing semantics.
