# Oyi Domain Maturity Matrix

Status: Programme 3 (Prediction + Forecasting + Outcomes/Learning + Proactive Intelligence) complete, built on Programme 2 (Room + Home Intelligence) and the Phase A/B/C + Programme 1 rollout matrix below.

Programme 3 added five anomaly detectors and four prediction providers (devices, maintenance, automations, security, visitors), one real forecast (utility spending), outcome evaluation for three prediction types, a bounded/human-gated learning-parameter module, a recommendation planner, and proactive delivery reusing the existing `NotificationService`. Four new conversational capabilities (`anomalies.read`, `predictions.read`, `forecasts.read`, `recommendations.read`) plus a new `intelligence` Home/Room contributor. See `OYI_PREDICTION_LEARNING_MODEL.md` for full detail. The Prediction/Anomaly/Outcome columns below are updated for the domains Programme 3 actually covers (devices, maintenance, automations, security, visitors, utilities); all other rows are unchanged from Programme 1/2.

Programme 2 added: `home.summary.read`, `home.attention.read`, `home.activity.read`, `room.status.read`, `room.attention.read`, `room.activity.read`, `rooms.inventory.read` (the last two promoted from `declared`/`shadow` stubs). These are AGGREGATORS, not new evidence — every contributor calls an existing Programme 1 evidence loader. See `OYI_ROOM_INTELLIGENCE.md` / `OYI_HOME_INTELLIGENCE.md` for the full contributor registry, coverage/severity model, and multi-domain result-set continuity. `home`/`rooms` rows below are updated accordingly; all other domain rows are unchanged from Programme 1 (device/security/maintenance status columns below describe the domain's OWN maturity, not its Room/Home contributor status — a domain can be a Home contributor without having a Room contributor, e.g. wallet/visitors/utilities/services/community have no real per-room relationship in the schema and are Home-only, documented in OYI_ROOM_INTELLIGENCE.md rather than fabricated here).

Direct Evidence correction: maintenance and visitors moved from context-backed (client-supplied `input.relationships`, no server-side authorization) to direct database evidence — `loadMaintenanceRequestFacts`/`loadVisitorAccessFacts` query `maintenance_requests`/`visitor_access` directly, scoped server-side by `home_id` (consumer surface) or `estate_id` (facility surface), with an explicit `unavailable` fact on query failure so empty is never confused with unavailable. Visitor access codes are redacted before becoming evidence. Both capabilities are now `enabled`.

Phase B separates vocabulary from production ownership. `enabled` means resolver, authority, evidence requirements, evidence loading, read handler, structured result status and presentation policy are all present and tested. `implemented`, `shadow` and `declared` capabilities are not advertised to end users as available.

Phase B correction: enabled read capabilities also persist through canonical Oyi conversation History. Wallet transaction evidence now follows the authorised home wallet relationship path. Utility active/usage/balance/meter reads remain below enabled and must not be answered by the utility spending handler.

Phase B final correction: resolved-but-not-enabled capabilities return safe canonical fallback responses instead of generic runtime failure wording. Capability advertising presentation no longer emits unrelated Home update artifacts, and source metadata is deduplicated into useful resident-facing labels.

Phase C adds durable conversation workflow/action persistence and device-first explicit-confirmation action orchestration. Device execution still uses the existing command pipeline; no other sensitive action domains are migrated in this phase.

Phase C correction: device action target resolution now uses the canonical named-device resolver before clarification, extracts channel/state/device from complete commands, and evaluates pending workflow clarification before ordinary read capability routing.

Phase C runtime correction: device action preparation now emits staged production traces, reports workflow/action persistence failures as safe structured outcomes, and no longer depends on a hard workflow/action foreign-key ordering against conversation thread persistence.

Phase C final multi-gang correction: independently controllable multi-channel devices cannot reach confirmation without an explicit valid channel. Channel candidates are loaded from device metadata/capabilities, persisted with the workflow, and confirmation binds the canonical channel code plus requested state.

Phase C reload correction: pending channel clarification and pending confirmation survive Consumer reload through canonical thread restoration. Thread APIs expose safe `active_workflow` metadata, and continuation is accepted only for the same authenticated actor/surface/scope/thread workflow, never by broad actor/home guessing.

Programme 1 direct evidence (first pass): utilities (active/tariff/purchases; usage/balance/meter deliberately kept below enabled — no consumption series, per-meter balance, or reading series exists in any production table), security (`facility_incidents`, the real actively-written incident table — not the near-empty `operational_incidents`), services (shared service-account loader with utilities, filtered differently), community (`community_posts`, official/pinned ranked ahead of chatter), scenes/automations (`consumer_scenes`/`consumer_automations`/`consumer_automation_runs`), and wallet balance (`wallets.balance`/`currency`/`is_frozen`, previously unselected) all moved from declared/legacy-fallback to enabled, evidence-backed `readModule` capabilities. Ten capabilities total; see `oyi-direct-evidence-programme1-smoke.mjs`.

Programme 1 deep-conversation closure (second pass): a single generic mechanism — not per-domain branches — now provides ordinal (first/second/third/last/latest/oldest), pronoun ("that one"/"it"/"tell me more"), attribute ("the failed one"), filter ("show only the high priority ones"), grounded explain ("why?"), status/field ("is it resolved?"/"where?"/"how much?"), temporal follow-up ("what about last week?"), and utility financial comparison ("which was higher?") across every enabled `readModule` capability, plus cross-domain context switching ("go back to that maintenance issue"). Architecture: `DomainResult → CanonicalObjectReferences → ThreadResultSetContext (per-domain, in oyi_conversation_threads.metadata.result_sets) → GenericFollowUpResolver → TargetHydration → DomainCapability → GroundedResponse`. See `src/oyi-core/context/resultSetContext.ts`, `src/oyi-core/interpretation/followUpResolver.ts`, `src/oyi-core/domains/explainAnswer.ts`, and the wiring in `ConversationOrchestrator.run()`. Legacy per-domain ordinal branches in `oyiUnifiedIntelligenceService.ts` remain as-is (untouched, not extended) — they serve a *different* route (`aiRoutes.ts`), not the capability pipeline this mechanism covers. No migration was needed; result sets live entirely in the existing thread metadata JSONB column. Hydration defects fixed in the same pass: phantom `utility_meters`/`facility_assets` table references removed (no such tables exist; now honestly `unsupported`), `wallet_transactions.currency` (nonexistent column — currency lives in `metadata.currency`) removed from its hydration select, and two previously-undiscovered missing hydration aliases added (`visitor_access`, `automation_run` — the evidence loaders' actual object types, which had no registry entry at all). See `oyi-programme1-deep-conversation-smoke.mjs`.
