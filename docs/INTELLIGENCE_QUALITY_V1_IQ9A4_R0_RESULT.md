## Fixes (root cause each)
1. **Visitor activity.** One definition, `domains/visitors/visitorPassState.ts` (`visitorPassState`): a pass is active only if status is active and no recorded expiry has passed; a pass recorded active with a passed expiry is `active_past_expiry` (neither active nor assumed expired); a missing or unparsable expiry leaves status to stand. Used by the record read (`visitorFromRow`, presentation rows), the deterministic judgment (`contextStatements`: "0 currently active, 1 recorded active but past its recorded expiry (validity not confirmed), …", never a bare zero) and the projector (validity questions state the conflict instead of Yes or none). Also fixed `visitorAccessStatus("inactive")` returning active.
2. **Affirmative licence.** `projector.ts`: a YES about someone looking at, handling, working on, assigning or acknowledging a record needs a progress, acknowledged or assigned status or an assignee in the record; otherwise "I can't confirm that anyone is working on it … unknown, not a no".
3. **Compound action consistency.** The IQ-9A2 split now uses the typed `requiresConfirmation`, `confirmations[]` and `execution.workflow_id`. A new pending proposal is shown with its own "Please confirm … No command was sent yet." plus "awaiting your approval; it has not been done, and the cancelled request was not carried over." Never "not started" when a proposal exists.
4. **Confirmation continuation.** An approval-sounding message that is not an exact confirmation form ("yes confirm please") no longer reaches the unsupported fallback. It is answered with the real pending state and the canonical mechanism (reply just "yes"/"confirm", or use the confirmation shown); with nothing pending it says nothing is waiting and a cancelled request cannot be revived. It executes nothing; exact forms still go through the unchanged `actionService.approve` path; cancellation remains terminal.
5. **Constraints.** `isCancellationSentence`: "do not share/disclose/reveal/expose/leak/publish … <specific thing>" is a disclosure constraint, not a cancellation (a bare "don't share it" still cancels). It no longer falls through to `financial.summary.read`. The existing acknowledgement already says "This holds for this conversation only" and contains no values; no durable-enforcement claim is made (a test pins this).
6. **Public handoff.** `composeCallbackAnswer` is exported with an injectable requester and `classifyHandoff` distinguishes accepted-with-receipt, rejected, unavailable, attempted-no-receipt and contact-completed (only when the Office receipt's own status says completed; acceptance never implies contact). Metadata: `handoff_stage`, `contact_completed`.
